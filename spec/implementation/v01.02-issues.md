## v01.02 Tasks

### ARENA-004 — Async Database Engine & Base Model

**Description:**
Sets up the foundational database engine using SQLAlchemy for async SQLite connections. This touches the `server/` module, specifically creating a new database config file.

**What needs to be done:**
- Add `aiosqlite` to `requirements.txt`.
- Configure SQLAlchemy with an asynchronous SQLite engine (`sqlite+aiosqlite:///arena.db`).
- Set up the session maker and declarative Base class for ORM models.

**Dependencies:** None

**Expected result:**
The server has a configured async database engine capable of creating sessions.

**Acceptance criteria:**
- [ ] `aiosqlite` is locked in requirements.
- [ ] SQLAlchemy async engine and declarative base are configured in a new DB module.
- [ ] **Unit test:** Pytest can successfully initialize the engine in-memory (`sqlite+aiosqlite:///:memory:`).
- [ ] Ties to Phase DoD.

### ARENA-005 — Database Schema Models

**Description:**
Defines the core persistence models required to store match state, moves, and chat messages. Touches the `server/` module.

**What needs to be done:**
- Define `MatchModel`: `id` (PK, string UUID), `status` (Enum: PENDING, ACTIVE, COMPLETED), `created_at` (Datetime).
- Define `MoveLogModel`: `id` (PK), `match_id` (FK), `player_id` (String), `move_payload` (JSON), `timestamp`.
- Define `ChatLogModel`: `id` (PK), `match_id` (FK), `sender` (String), `message` (Text), `timestamp`.

**Dependencies:** ARENA-004

**Expected result:**
The SQLAlchemy schema correctly maps the game state entities with appropriate relationships and foreign keys.

**Acceptance criteria:**
- [ ] `MatchModel`, `MoveLogModel`, and `ChatLogModel` classes are fully defined.
- [ ] Foreign keys strictly enforce relationships.
- [ ] **Unit test:** Pytest verifies the schema creation succeeds without syntax or mapping errors.
- [ ] Ties to Phase DoD.

### ARENA-006 — Repository Pattern CRUD

**Description:**
Abstracts the database layer away from the networking logic by implementing a Repository class. Touches the `server/` module.

**What needs to be done:**
- Implement a `Repository` class containing asynchronous methods for standard operations.
- Create methods to insert a match, fetch a match by ID, log a move, fetch move logs for a match, log a chat message, and fetch chat logs.

**Dependencies:** ARENA-005

**Expected result:**
Other modules can query and mutate the database without directly importing SQLAlchemy logic.

**Acceptance criteria:**
- [ ] `Repository` class is implemented with type-hinted async CRUD methods.
- [ ] Methods properly utilize SQLAlchemy async sessions.
- [ ] **Unit test:** Pytest executes a basic write and read cycle using the repository against an in-memory DB.
- [ ] Ties to Phase DoD.

### ARENA-007 — Database Verification Script & Tests

**Description:**
Validates that the database schema and repository can handle realistic data insertion, fulfilling the Phase DoD. Touches the `server/` module and `tests/`.

**What needs to be done:**
- Create a standalone Python script (e.g., `server/init_db.py`) that successfully instantiates the database schema and inserts dummy records for matches and chat logs.
- Write comprehensive database unit tests verifying foreign key constraints.

**Dependencies:** ARENA-006

**Expected result:**
The database layer is fully verified as functional and ready to be integrated into the WebSocket logic in the next phase.

**Acceptance criteria:**
- [ ] Initialization script runs cleanly and outputs success metrics.
- [ ] **Unit test:** Pytest verifies that inserting a `MoveLogModel` for a non-existent `match_id` fails (Foreign Key constraint validation).
- [ ] Ties to DoD: Script successfully instantiates the database schema and queries dummy records.
