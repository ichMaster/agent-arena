## Findings

### #1 🟡 `current_turn` replays the move log twice (LOW) — deferred
`Repository.current_turn` calls `reconstruct_game(match_id)` (which runs `_moves_in_order` + replays
every move through a fresh `TicTacToe`) and then calls `_moves_in_order(match_id)` **again** to count
moves for the parity. So every "whose turn" query does the moves SELECT + full replay twice. At MVP
scale (one match, ≤9 moves, SQLite) this is computationally irrelevant, but it is a real avoidable
pattern — e.g. count from the same list the reconstruction already loaded, or return `(game, count)`
from one pass. Homed to **v05.01** alongside the roadmap's other resilience/perf polish, not fixed now.

## What's solid
`assign_symbol` is genuinely race-safe: two connections claiming the last free symbol both pass the
read, but `UNIQUE(match_id, symbol)` fails one commit; that caller rolls back and **retries**,
re-reading the now-updated taken set (getting the other seat, or `None` if full), bounded by
`len(_SYMBOLS)+1` so it always terminates — proven by an `asyncio.gather` race on two separate
sessions that resolves to `{X, O}` deterministically. FK enforcement is real (the connect-time
`PRAGMA foreign_keys=ON` listener is verified on a fresh connection, and an orphan `Move` is rejected).
The move payload is stored opaquely (a dict round-trips untouched — the store never parses it). `NullPool`
+ temp-file test DBs keep many short-lived engines from colliding, and the code comments correctly flag
that `NullPool` + `:memory:` would be unsafe. `current_turn` correctly returns `None` at *and after*
the terminal move, and parity (`X` on an even count) is exactly the §5.1 design — sound because the
only writer (arriving v01.04) will validate alternation before logging.
