## Findings

### #1 🟡 Malformed JSON drops the connection (LOW) — deferred to v05.01
`_ws_connection`'s loop calls `await websocket.receive_json()`; a client sending non-JSON text raises
`json.JSONDecodeError`, which isn't `WebSocketDisconnect`, so it propagates to the `finally` (cleanup
runs correctly) and the socket dies rather than getting an `error` event and staying open. Only the
offending client is affected — no other connection or the server is harmed. This phase's own
scope-note and the reconcile explicitly home "malformed-JSON-kept-alive" to **v05.01** (resilience),
so it is deferred, not fixed here.

### #2 🟡 Observer chat is accepted (LOW) — deferred to v03.03
`_handle_action`'s `chat` branch accepts a message from a seatless connection and broadcasts it as
`sender="observer"`. game_spec §3.3 says observers watch read-only in the MVP. But the Observer *role*
(and any UI that would enforce read-only) is introduced in **v03.03**; enforcing it server-side is
most coherent there, alongside the role it belongs to. Deferred to v03.03 (its natural home), not
pulled forward into the transport phase.

## What's solid
The move authority is **naturally race-safe without a lock**: `current_turn` is always re-derived from
the *actually committed* move log (never cached), so two connections' interleaved `submit_move`
handlers can't both apply — whoever commits first flips the derived turn, and the other's turn-check
(reading the committed log) rejects with "not your turn". `apply_move` remains the sole legality
authority, so a malformed `move` payload (wrong type, out of range, `None`) is rejected there as
"invalid move" and never crashes the handler. The `finally` cleanup uses `asyncio.shield` around the
seat release, which is exactly what §10 requires — the TestClient WS-context-exit surfaces as task
cancellation, and the shield keeps that cancellation from interrupting the release's own commit
(reclaim-after-drop is deterministic across repeated runs). `broadcast` serializes once and prunes a
dead socket, so one bad client can't block delivery; after `close_room` the per-connection `finally`
paths are all idempotent (`disconnect` returns `None` the second time). No model or secret is involved
this phase.

## Architecture impact
None — §5.3/§5.4/§6.2/§10 implemented exactly as documented. The `asyncio.shield` in the finally is an
implementation of §10's already-stated "only `finally` reliably releases the seat" guarantee, not a
new contract.
