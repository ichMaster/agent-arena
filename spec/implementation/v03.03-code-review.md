## Findings

### #1 🟠 Observer chat not server-refused (MEDIUM)
**Scenario:** a forced WS `chat` frame from a seatless (`spectator:true`) connection is currently
**accepted** by `_handle_action` — logged and broadcast as `sender="observer"`. The shipped UI never
sends this (the Observer's chat input is disabled), but any other WS client (a script, curl, a
modified page) can post chat into a match it's only supposed to watch — the client-side suppression is
the *only* guard, exactly the failure mode §5 warns about for `submit_move` ("the UI must not depend on
that as its only guard"). This is the **observer-read-only-chat item this branch's v01.04 review
explicitly deferred to v03.03**, now due. **Proposed fix:** `_handle_action`'s `chat` branch refuses a
seatless connection with `error_event("observers cannot chat")` (mirroring the existing `submit_move`
"no seat" refusal) and returns without logging or broadcasting, plus a regression test.

## What's solid
`renderChat`/`renderSystem` build DOM nodes and set `.textContent` only — no `innerHTML` anywhere, so
chat content can't inject markup. `chat_message.sender` is derived server-side from the connection's
actual assigned symbol, never trusted from the client payload — no spoofing. The chat form never
renders optimistically (only the server's echo renders a bubble). `renderPlayers`'s Observer branch is
a pure presentation change and correctly avoids `null.toLowerCase()`.

## Architecture impact
Behavioral, not a wire-shape change: the `chat` action's server-side authorization will match
`submit_move`'s pattern (seatless → `error`) — no new event/action, so `spec/architecture.md` §6.2 is
unaffected (it already frames chat as a player action).
