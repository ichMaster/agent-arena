## Findings

### #1 🟡 Fast-reconnect release ordering (LOW) — accepted
If a client reconnects on the same token *before* the previous socket's `finally` shield-release runs,
that late release can set the DB `symbol` to `null` after the reconnect already reclaimed it.
**Why it's benign:** every seat-dependent action (`submit_move`) re-runs `assign_symbol`, which
re-grants the first free seat, so the reconnected player is re-seated on their next move — the state
self-heals and no move is wrongly rejected in the 2-player game. The new tests retry-settle around this
window to stay deterministic. A stricter "don't release a seat that a live connection re-owns" guard is
possible but is new hardening beyond v05.01's verification scope (explicitly out of scope per the
user's checkpoint decision). Recorded for a future consideration if multi-seat games arrive.

## What's solid
The WS cleanup runs in `finally` under `asyncio.shield` (cancellation-safe); broadcast prunes a dead
socket and still delivers to the rest; malformed JSON and bad tokens are handled without stranding a
match; model errors degrade to a legal fallback. All paths are now tested, deterministically.
