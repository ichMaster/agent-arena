# Code Review & Fix Recommendations — v01.01 (project skeleton & the game engine)

**Date:** 2026-07-21 · **Reviewer:** Claude Opus 4.8, via `/ship-solution`
**Scope:** `games/interface.py`, `games/tictactoe.py`, `pyproject.toml`, and their tests.
**Method:** manual adversarial read of the engine — every path through `apply_move` for a possible
raise, the win-vs-draw ordering in `is_game_over`, the terminal-board behavior of `get_valid_moves`,
and the type guards; each concern chased to a concrete input.

## Recommendation summary

*No findings.* The engine is the sole legality authority exactly as §4.1 requires, and every illegal
input category is rejected with `False` rather than an exception.

## Findings
None.

## Notes considered and set aside (not findings)

- **The engine does not enforce turn order** — `apply_move("X", …)` then `apply_move("X", …)` again is
  accepted, and `O` may legally move first. This is **intentional, not a gap**: per architecture §5.4,
  whose-turn-it-is is a *derived* server-side condition (`current_turn` computed by replaying the move
  log), and the `GameInterface` is deliberately turn-agnostic so live state can be reconstructed from
  the log without the engine holding turn state. Pulling alternation into the engine would violate that
  separation. Turn-order authority arrives with the server in v01.04, re-validated server-side.
- **`_WINNING_LINES` is imported by `test_tictactoe.py` as a private name.** Deliberate: the test
  parametrizes over the exact same line table the engine uses, so "win on every line" can't silently
  drift out of sync with the implementation. A copy in the test would be the worse option.

## What's solid
`apply_move` cannot raise on any input: the game-over check, the `player not in _SYMBOLS` check, the
`isinstance(move, bool) or not isinstance(move, int)` guard (which correctly rejects `True`/`False`
*before* they could pose as cells 1/0), and the `0 ≤ move ≤ 8` range check all run before the single
`self._board[move]` access, so no `IndexError`/`TypeError` is reachable. `is_game_over` checks the 8
winning lines before the draw condition, so a full board that also contains a line returns the winner,
never `"draw"`. `get_valid_moves` returns `[]` at a won board even with empty cells remaining (a won
board is terminal — no player to move). `get_state` returns a *copy* of the board, so a caller can't
mutate engine state. The `pyproject.toml` packaging pin (`packages = ["games","server","agent"]`)
pre-empts the setuptools flat-layout error before it can bite. No model is touched anywhere this phase.

## Architecture impact
None — `GameInterface` (§4.1) and the §2 layout implemented exactly as documented; no contract changed.
